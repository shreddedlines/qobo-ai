# HTTP API

Base path `/api`. Every endpoint except health requires `Authorization: Bearer <Supabase access token>`. The user is always taken from the verified token, never from the request body. Errors use a single JSON shape:

```json
{ "error": { "code": "not_found", "message": "Conversation not found", "details": {} } }
```

| Code | HTTP | When |
| --- | --- | --- |
| `bad_request` | 400 | Invalid body or query (`details` lists the fields) |
| `unauthorized` | 401 | Missing, malformed, invalid or expired token |
| `not_found` | 404 | Unknown route, or a conversation that doesn't exist or belongs to someone else |
| `conflict` | 409 | `clientMessageId` already used in a different conversation |
| `payload_too_large` | 413 | JSON body over 32 KB |
| `rate_limited` | 429 | Per-IP limit: all API routes (default 120/min) or chat (default 20/min) |
| `quota_exceeded` | 429 | Per-user daily message cap reached (`details`: `limit`, `used`, `resetsAt`) |
| `service_unavailable` | 503 | Auth service unreachable, or the assistant's model/search is unavailable (`Retry-After` header) |
| `timeout` | 504 | A chat turn took longer than `CHAT_REQUEST_TIMEOUT_MS` (default 45s) |
| `internal_error` | 500 | Anything unexpected (details are logged, never returned) |

## Health

- `GET /api/health` → `{ "status": "ok" }` (liveness, not rate limited)
- `GET /api/health?deep=1` → `{ "status": "ok", "database": "ok" }`, or HTTP 503 with `"degraded"` / `"unavailable"`

## Conversations

- `GET /api/conversations?limit=20&before=<ISO timestamp>` → `{ conversations: ConversationSummary[], nextCursor: string | null }`, newest first
- `GET /api/conversations/:id/messages` → `{ conversation: ConversationSummary, messages: ChatMessage[] }`, oldest first
- `PATCH /api/conversations/:id` → `ConversationSummary`. Renames a conversation: `{ "title": "Pricing questions" }`, trimmed, 1–120 characters after trimming (an empty or whitespace-only title is a 400). Only the title changes — `updatedAt` is left alone, so renaming does not reorder the list — and Row Level Security limits the update to the caller's own conversations, so someone else's id is a 404.
- `DELETE /api/conversations/:id` → 204. The conversation's messages are deleted with it. The daily message count is not reduced.

## Chat

`POST /api/chat`

```json
{
  "message": "How much is the Pro plan?",
  "clientMessageId": "<uuid v4 generated by the client>",
  "conversationId": "<uuid, omit or null to start a new conversation>",
  "replaceMessageId": "<uuid, optional: edit this saved user message in place>"
}
```

→ 200

```json
{
  "conversation": { "id": "…", "title": "How much is the Pro plan?", "createdAt": "…", "updatedAt": "…" },
  "userMessage": { "id": "…", "role": "user", "content": "…", "intent": null, "status": null, "sources": [], "createdAt": "…" },
  "assistantMessage": {
    "id": "…", "role": "assistant", "content": "Pro is listed at ₹999 [1]. …",
    "intent": "qobo", "status": "answered",
    "sources": [{ "title": "Plans & Pricing", "url": "https://qobo.dev/plans", "kind": "qobo" }],
    "createdAt": "…"
  },
  "replayed": false
}
```

- **`message`:** trimmed; 1–2,000 characters.
- **`intent`:** `qobo`, `general`, `off_topic` or `smalltalk`.
- **`status`:** `answered`, `insufficient` (the assistant couldn't answer from its sources) or `redirected` (off-topic request).
- **Citations:** `[n]` markers in `content` refer to `sources[n-1]`. `kind` is `qobo` (QOBO's website) or `web` (general web research).
- **Idempotency:** retrying with the same `clientMessageId` returns the saved exchange with `replayed: true`. There is no second model call and no quota charge. Generate a new id for each new message, and reuse it only when retrying that message.
- **`replaceMessageId`** (optional): edit a message. The named message must be the caller's own **user** message in `conversationId`, which is then required. Instead of appending, the reply is regenerated and both rows are updated in place by `replace_exchange`, so the exchange keeps its position, its ids and its conversation, and no second version is stored. An assistant message can never be named: the SQL function matches `role = 'user'`, so a reply, a foreign message or an unknown id all return 404. The history used for regeneration is the conversation *before* that message, and the turn costs one message from the daily cap like any other. Nothing is written until the reply exists, so a 503 or 504 leaves the conversation exactly as it was.

### Order of operations

1. Validate the body.
2. If this `clientMessageId` was already saved, return it (`replayed: true`).
3. For an existing conversation, load it with the user's token (Row Level Security applies): 404 if it isn't the caller's. Its last 10 messages become the model's history.
4. Count one message against the user's daily cap (`USER_DAILY_MESSAGE_CAP`, default 50, resets at 00:00 UTC): 429 `quota_exceeded` when the cap is reached.
5. Run the chat pipeline (router → QOBO answer / web research / fixed reply) under `CHAT_REQUEST_TIMEOUT_MS`.
6. Save the user message and assistant reply atomically with `append_exchange`. This creates the conversation on the first message, titled from that message.

If step 5 fails (503) or times out (504), **nothing is saved**, and the client can retry with the same `clientMessageId`. That attempt has already counted against the daily cap. If the conversation is deleted while a reply is being generated, the save fails with 404.

The assistant message's stored metadata (not returned by the API) records the reply status, router source, model and language, the answer path's outcome, models, web-search status, guards applied, and latency. It never contains prompts or keys.
